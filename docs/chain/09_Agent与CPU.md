# 09 · Agent 时代的 CPU：tool call 到底吃什么硬件

> 问题来源（2026-10）：「agent 这么火，下一步肯定是低成本本地部署、个人 agent，这些是不是都需要
> 很多 CPU 参与，比如 tool call / function call？那是不是说明 AMD 和 Intel 还可以买？」
>
> 这是一条四环推理链。本篇的任务不是给结论，是把每一环拆到**可以用数量级检验**的程度——
> 这正是「金融体系化思维」在产业链研究里的样子：先把因果链写出来，再逐环找数据证伪。
> 方法与第 06 篇（算力经济学）相同：**性能几乎总是数据搬运问题，不是算力问题**。

---

## 1. 先看一次 agent 循环的数据流：时间花在哪

一次典型的 agent 步骤（以编码 agent 为例）：

```
上一步结果/用户输入 ──► prompt 组装 ──► tokenizer ──► prefill ──► decode(逐 token) ──► 停止
       ▲                 CPU ~ms        CPU ~ms      GPU/NPU      GPU/NPU 100ms~20s
       │                                             10ms~数秒
       └── 结果回填 ◄── 工具执行 ◄── 路由/校验 ◄── 解析 tool call JSON
            CPU ~ms      看工具:        CPU ~µs        CPU ~µs~ms
                         µs(读文件)~分钟(跑测试)
```

逐段给数量级（标注硬件代际，都是 batch=1 的本地/单用户场景估算）：

| 环节 | 落在哪 | 数量级 | 决定因素 |
|---|---|---|---|
| tokenizer（BPE，Rust 实现） | CPU | ~1 µs/token → 10k token ≈ 10 ms | 单核标量性能，与核数无关 |
| prefill（处理 prompt） | GPU/NPU/CPU | FLOPs ≈ 2 × 参数量 × token 数。8B 模型 × 4k token ≈ 64 TFLOP：H100(~990 TFLOPS BF16) ≈ 0.1 s；RTX 4090(~165 TFLOPS 稠密) 按 50% 利用率 ≈ 0.8 s；桌面 16 核 CPU(AVX-512 ~1–2 TFLOPS FP32) ≈ 30–60 s | **算力**（compute-bound） |
| decode（逐 token 生成） | GPU/NPU/CPU | 每生成 1 个 token 要把全部权重读一遍。8B@4-bit ≈ 4.5 GB/token：DDR5 双通道(~90 GB/s) ≤ 20 tok/s 理论、10–15 实测；Apple M4 Max(546 GB/s) ~80–100；RTX 4090(1 TB/s) ~150–200；H100(3.35 TB/s) 单流 300+ | **内存带宽**（memory-bound） |
| 解析 tool call JSON | CPU | 1 KB JSON ≈ 微秒级 | 可忽略 |
| 路由/参数校验/权限 | CPU | 微秒到毫秒 | 可忽略 |
| 工具执行 | CPU / IO | 读文件 µs–ms；shell 命令 ms–s；网页抓取 0.1–2 s（**网络等待，CPU 空闲**）；跑测试/编译 秒–分钟（真正 CPU-bound） | 取决于工具本身 |
| 结果回填 + 下一轮 prefill | GPU | 只处理**新增** token（KV cache 复用），通常 <0.1 s | 增量 |

一眼就能看出的结论：

**「tool call / function call 需要很多 CPU」在技术上不成立。** 调用本身（解析、路由、分发）
是微秒级工作，比一次模型生成小 4–6 个数量级。真正占 CPU 的是**工具执行的内容**——而那是
普通软件工作负载（跑测试、编译、处理数据），它们在 agent 出现之前就存在，agent 只是把人类
按回车的频率提高了。

这里有一个常见的认知错位值得点破：很多人把「agent 做了很多事」等同于「CPU 很忙」。
但从数据流看，agent 循环里 CPU 大部分时间在**等**：等 GPU 吐 token、等网络返回、等磁盘。
等待不消耗 CPU 周期，也不卖 CPU。

## 2. 本地部署的真实瓶颈：内存带宽与容量，不是 CPU 核数

这是本篇最有杠杆的一个物理事实，用 Roofline 一句话说清：

> decode 的算术强度极低（每读 1 字节权重只做 ~2 次乘加 / 批大小），远在 ridge point 左侧，
> 所以**给它更多算力毫无用处**，唯一有用的是更快地把权重搬进计算单元。

推论一：**CPU 核数翻倍，本地模型 tok/s 几乎不变**——因为瓶颈是内存通道而不是 ALU。
桌面平台无论 8 核还是 24 核，都是双通道 DDR5，~90 GB/s 封顶。

推论二：真正拉动「本地 AI」体验的硬件参数是：
- **内存带宽**：决定 tok/s。这就是为什么 Apple 统一内存（M4 Max 546 GB/s）、AMD Strix Halo
  （256-bit LPDDR5X，~256 GB/s）、独显（4090 1 TB/s）能跑 30B 级模型而普通笔记本不能。
- **内存容量**：决定能装多大的模型。30B@4-bit ≈ 17 GB，70B@4-bit ≈ 40 GB。消费级独显 24 GB
  是硬墙；统一内存 64–128 GB 是 Apple/Strix Halo 的卖点。
- **NPU（40–50 TOPS int8）**：主要帮 prefill 和小模型，decode 仍受带宽限制。

推论三：**「本地 agent」的硬件受益者是「带宽大、容量大的 SoC + 更多 DRAM/LPDDR」**，
即 AI PC 平台（Apple M、AMD Strix 系、Intel Lunar/Panther Lake、Qualcomm X）与**存储厂**。
这把问题从「CPU 厂商」改写成了「平台 SoC + 内存」——AMD/Intel 确实在里面，但受益的是它们的
**客户端 SoC 业务**，通过 PC 换机周期与 ASP 提升兑现；而且同一逻辑下，每台 AI PC 多装的
16–32 GB 内存对 DRAM 厂（第 03 篇）的边际拉动，可能比对 CPU 厂更干净。

推论四：**本地部署会不会成为主流**本身存疑。前沿模型能力每年仍在拉开差距、云端 token 价格
每年下降数倍（第 06 篇的「需求 vs 效率赛跑」），本地部署的经济性只在隐私/离线/高频小任务
三类场景成立。「下一步肯定是本地部署」是一个需要被证据支持的判断，不是必然。

## 3. 数据中心侧：agent 对 CPU 的拉动有多少是真的

三个渠道，强弱不同：

**渠道 A：GPU 服务器的 host CPU（弱，甚至在变弱）。**
- DGX H100 / HGX B200：每 8 张 GPU 配 2 颗 x86（Xeon 8480C / 8570）→ 0.25 CPU/GPU，
  约 14 核/GPU。
- GB200 NVL72 / GB300：每 72 张 GPU 配 36 颗 **Grace（ARM）** → 0.5 CPU/GPU，但**不是 x86**。
- 所以每张 GPU 带来的 x86 需求：HGX 形态持平，NVL 机柜形态归零。agentic 工作负载没有改变
  这个配比——配比由 NVIDIA 的参考设计决定，不由工作负载决定。

**渠道 B：通用云计算——agent 的沙箱、编排、检索、数据管道（真实，但要算钱）。**
- 每个 agent 任务确实需要一个执行环境（容器/VM）跑工具：这是真实的 vCPU 需求，而且
  是 agent 出现之前没有的增量。
- 算一笔账：vCPU 小时 ~$0.03–0.05 vs H100 小时 ~$2–3（2026 租赁价）。一个 10 分钟、
  4 vCPU 沙箱的编码任务 CPU 成本 ≈ $0.03；同一任务的模型 token 成本 ≈ $0.5–5。
  **CPU 占 agent 任务成本的 1–5%。** 单位数量很多，美元很少。
- 它对 AMD/Intel 的意义是通过**云厂通用实例总量增长**兑现的——这是一个本来就存在的
  增长曲线（10–20%/年），agent 让它稍陡一点；其中 AMD 的份额在上升（EPYC 服务器收入
  份额从 2022 的 ~20% 升到 2026 的 ~35–40% 量级，核实见当期报告），Intel 在下降。

**渠道 C：CPU 推理（小模型、embedding、rerank）——Intel 的叙事，规模有限。**
- AMX/VNNI 让 Xeon 跑 1–8B 模型与 embedding 可用，但每 token 成本仍高于 GPU 批处理。
  只在延迟不敏感、规模小、GPU 排不上队的场景成立。

把三条合起来：**agent 对数据中心 CPU 的拉动是「通用云增长的一部分」**，不是像 HBM/CoWoS
那种「每张 GPU 必配、供给刚性」的物理耦合。第 02/03 篇里「需求远大于供给」的结构，在 CPU 上不存在。

## 4. 把推理链逐环打分

| 环 | 命题 | 判定 | 依据 |
|---|---|---|---|
| ① | agent 火热 | 成立 | 用量数据（见当期报告） |
| ② | 下一步是低成本本地部署/个人 agent | **部分成立** | 只在隐私/离线/高频小任务场景；云端能力与价格曲线仍占优（第 06 篇） |
| ③ | tool call 需要很多 CPU | **不成立** | 调用本身微秒级；重的是工具内容，且多为 IO 等待 |
| ④ | 所以 AMD/Intel 可买 | **因果链断裂** | ③ 不成立 → ④ 不能从 ①② 推出；AMD/Intel 要单独立论 |

AMD 与 Intel **真正的**多头论点（与 agent 无关或只弱相关）：
- AMD：MI350/MI400 GPU 在推理市场的份额（这是 AMD 过去一年涨幅的主因，不是 CPU）；
  EPYC 服务器份额继续从 Intel 手里拿；客户端 Strix/Zen 6 的 ASP。
- Intel：18A 制程与代工客户落地；政府持股与 NVIDIA 投资带来的「不会倒」折价修复；
  Panther Lake 的 AI PC 换机周期（Windows 10 停服驱动）。

真正的空头论点：
- 两家的股价在过去一年已经翻倍以上（见当期报告的估值表）——市场已经为「AI 带动 CPU」
  这个模糊叙事付过钱；
- ARM 在数据中心（Grace、Graviton、Axion）与 PC（Apple、Qualcomm）两端同时侵蚀 x86；
- 通用云增速是个位数到低双位数，撑不起半导体级别的估值扩张。

**能分辨多空的数据**（放进调研状态机 `cpu_agentic_compute` 节点的触发器）：
1. Mercury Research 季度服务器 CPU 份额（AMD 是否继续 +2–3pp/年）。
2. 云厂财报里通用实例 vs 加速实例的增速（AWS/Azure 不直接披露，看 capex 结构与
   Intel/AMD DCAI 收入增速的差）。
3. NVIDIA 机柜出货中 NVL（Grace）vs HGX（x86）的比例。
4. AI PC 的 ASP 与内存配置（每台 ≥32 GB 的比例）——这项同时是 DRAM 节点的触发器。
5. AMD 数据中心收入中 GPU 与 CPU 的拆分方向。

## 5. 投资视角的收束

这条推理链的教训是通用的：**「X 很火 → X 需要 Y → 卖 Y 的公司可买」**，中间那一环必须用
物理/经济数量级检验，而不是用直觉。本轮检验的结果是：agent 确实需要 CPU，但需要得**很少**，
并且需要的是**内存带宽**而不是 CPU 核——所以如果硬要从「个人 agent」找硬件受益者，
顺序是：内存（容量+带宽）> 平台 SoC（AI PC 换机）> 通用云实例（AMD 份额）> 「CPU 因 tool call 受益」。

AMD/Intel 该不该买，要回到它们各自的 GPU/代工/份额论点上去，用 `finloop analyze` 看估值
与趋势，用 `finloop size` 算仓位——而不是因为 agent。
