# 数据质量解决方案

> 实现：`src/finloop/data/`。
> 离线演示：`finloop quality --demo`（故障注入 → 判定 → 降级全流程可视化）。
> 真实检查：`finloop quality NVDA`（需要网络）。

## 设计原则

**坏数据宁可拒绝，不可静默流入指标层。** 一个被污染的收盘价序列会让所有
下游输出（指标、信号、回测）变成看起来正常的错误答案——这比报错危险得多。

## 管线全景

```
请求 get_daily(ticker)
   │
   ▼
① parquet 本地缓存 ──命中且TTL内──► 返回（日线 TTL 6h，分钟线 30min）
   │ 未命中
   ▼
② 主源 yfinance（指数退避重试 ×3：2s/4s/8s）
   │ 异常或↓
   ▼
③ validate_ohlcv 质量校验
   │   ├─ error（结构性）→ 拒绝该源 → ④
   │   └─ warning（统计性）→ 放行 + 记录日志
   ▼
④ 按市场路由的备源降级（重复 ②③，见 providers/regional.py）：
     .TW/.TWO → 台湾证交所/柜买官方 ｜ .KS → Naver
     美股 → Tiingo（需免费key）→ Stooq（已被反爬墙，最后手段）
     其他市场 → 暂无备源
   │ 全部被拒
   ▼
⑤ repair_ohlcv 孤立坏行修复（最后手段）：
     坏行 ≤ max(5行, 0.5%) → 剔行放行，修复说明并入 warnings 显形
     大面积污染 → 不修（掩盖比拒绝危险）
   │ 仍失败
   ▼
⑥ 返回空 DataFrame + 拒绝报告（上层显式处理"无数据"，绝不拿到坏数据）
```

为什么需要 ⑤（2026-06 实测）：000660.KS（SK海力士）等 8 个日韩港中标的的
yfinance 五年日线各有 2-5 处孤立坏行，整票拒绝意味着 1200+ 行数据因 3 行
报废、HBM 双雄缺席横截面回测。修复纪律：只修结构性坏行、只修极少量、
修复行为必须出现在质量报告里——干净的备源数据永远优先于修补过的主源数据。

## 校验规则与真实故障的对应

| 检查 | 级别 | 真实世界的来源 |
|------|------|----------------|
| 空数据 / 缺列 | error | API 改版、代码错误 |
| 非正价格 | error | API 坏记录、停牌占位符 |
| OHLC 自洽（high≥max(o,c)、low≤min(o,c)） | error | 复权计算错误、数据拼接错误 |
| 时间戳重复 / 乱序 | error | 分页拉取重叠、时区折叠 |
| 极端跳变（>8×前期波动且>12%） | warning | 未调整的拆股除权、坏 tick |
| 连续零成交量 | warning | 数据缺失、退市边缘 |
| 交易日缺口（>7 自然日） | warning | API 部分返回 |

为什么跳变只是 warning：真实的暴涨暴跌（财报、FDA、并购）与坏数据在
统计上不可区分，自动拒绝会把真行情扔掉。所以放行 + 显式警告 + 留给
双源对账裁决。

一个实现细节：跳变阈值用的是**前一日为止**的滚动波动率（shift(1)）。
否则跳变本身会抬高窗口内波动率、抬高自己的阈值而逃过检测——
这个 bug 在开发中真实出现过，由测试抓出。

## 双源对账（独立性验证）

`finloop quality NVDA` 同时从主源和备源独立拉取，比较重叠日期
收盘价：平均偏差、最大偏差、超容差（1%）天数。

备源现状（2026-06 换代，按市场路由；实网验收 2026-06-12）：

| 市场 | 备源 | 复权口径 | 状态 |
|------|------|----------|------|
| 美股 | Tiingo（`TIINGO_API_KEY` 环境变量，免费注册） | 拆股+分红全调整，与 yfinance 同口径 | ✅ 已实网验证（需 key；验收时修了 1 个解析 bug，见下） |
| 美股（无 key 时） | Stooq | 仅拆股 | ⚠️ 已对数据中心 IP 部署反爬验证，云端基本不可用 |
| .TW 上市 | 证交所 TWSE 官方开放数据 | **未复权** | ✅ 已实网验证 |
| .TWO 上柜 | 柜买中心 TPEx 官方开放数据 | **未复权** | ✅ 已实网验证 |
| .KS 韩股 | Naver 金融 | 拆股调整（分红存疑） | ⚠️ 仍未实网验证* |
| .T/.HK/.DE/… | 暂无 | - | 日本可后续接 J-Quants（免费注册） |

\* 两轮环境都没放行：第一轮域名不在白名单；第二轮（2026-06-12）域名
已加白名单，但 egress 代理对 api.finance.naver.com 还有一层附加整域
拦截（任意路径/方法均被代理 403 "Blocked by egress policy"）。解析
逻辑仍只过离线单测。管线对该故障的降级行为已实测：`finloop quality
000660.KS` 显式报"备源失败 403"并标明路由，不静默。

口径差异（解读对账结果必须知道）：复权口径不同的两源，**最近一次
分红/除权之后的区间应几乎一致**；更早历史会有系统性偏差（未复权源
在拆股日附近还会触发"极端跳变"警告——属预期行为，不是数据坏）。

### 实网验收结果（2026-06-12，对账窗口 6 个月）

| 命令 | 备源路由 | 重叠 | 平均偏差 | 最大偏差 | 超容差(1%) | 结论 |
|------|----------|------|----------|----------|------------|------|
| `quality 2330.TW` | TWSE | 117 天 | 0.42% | 0.59% | 0 天 | 预期内：偏差是干净的"除息阶跃"（-0.59% → -0.27% → 0.00%，台积电季度除息各一级），最近一次除息后两源**逐日一致**——纯复权口径差异 |
| `quality 3081.TWO` | TPEx | 117 天 | 0.000% | 0.000% | 0 天 | 联亚近 6 个月无除息 → 未复权=复权，两源完全一致 |
| `quality 000660.KS` | Naver | - | - | - | - | 未能验证：备源被环境代理整域拦截（见上注*）；降级路径行为正确 |
| `quality MU` | Tiingo | 124 天 | 0.003% | 0.005% | 0 天 | 同为全复权口径，只剩复权因子的浮点舍入噪音 |

验收中发现并修复的问题（修复均有回归测试，样本取自真实响应）：

1. **Tiingo 重复列名崩溃（真 bug）**：真实响应里原始列（`close` 等）与
   复权列（`adjClose` 等）并存，provider 直接 rename 后产生两个同名列，
   质量门 `df["close"]` 取出 DataFrame 而非 Series，抛 ValueError——
   质量门自己先崩了。修复：rename 前只挑 adj* 列；同时 validate_ohlcv
   新增"重复列名"结构检查（按 error 拒绝而不是崩溃）。教训：这个
   provider 当初恰恰**没**被标"待实网验证"（它有离线测试、只是 mock
   没造出双列并存），带 bug 的正是它——标注与离线测试都不能替代实测。
2. **TPEx 字段名勘误（数值无错）**：实际字段是「成交張數」而非注释里
   写的「成交仟股」；1 張 = 1000 股，×1000 换算碰巧等价。注释与测试已
   对齐真实字段。成交量与 yfinance 同量级但有 ~5-15% 残差（两边对盘后
   定价/鉅额交易的统计口径不同）；成交量仅用于零量检测，可接受。
3. **对账输出的陈旧标注**：`finloop quality` 硬编码"yfinance vs stooq"，
   而实际备源已按市场路由。现改为打印真实路由（如 `yfinance vs
   regional-fallback:taiwan-official`），备源失败时也标明死的是哪个子源。

附注：台股两源在 6 个月窗口内各报 1 处"交易日缺口（12 天）"警告，
实为 2026-02-11 → 02-23 的春节休市——日历事实而非数据缺失（缺口
警告阈值只对 ≤7 自然日的假期静默）。

## 缓存

parquet 格式（保留 dtype 与时区），键 = (ticker, interval, period)。
价值：抵抗 Yahoo 限流（日报一次扫几十个标的）、提供离线复跑能力、
研究迭代时不重复打 API。损坏的缓存文件视为未命中并删除。

## 基本面字段的一致性防线（2026-06 新增）

行情（OHLCV）之外，估值筛选还依赖 yfinance 的基本面快照字段——
而它们出过比"缺失"更危险的事故：**静默错误**。实测案例（2026-06）：
3110.T 的 forwardPE 给 58.5（券商共识实为 ~18，差 3 倍）；MU 的
forwardPE 8.2 用的是两年外峰值盈利预估。错的数据长得和对的一模一样，
覆盖率（coverage）列暴露不了它。

`fundamentals.validate_fundamentals()` 把人工抓错的两个方法自动化：

| 检查 | 触发条件 | 抓的是什么 |
|------|----------|------------|
| fPE/tPE 偏离 | 比值 >3 或 <1/3 | 过时共识、远期财年口径、盈利将崩/周期顶外推 |
| 隐含净利率 | 市值÷fPE÷营收TTM >60%（>100% 升级措辞） | fPE 与市值/营收数学上不相容 |

输出进 `finloop screen` 的"数据预警"列。**预警只提示"先核验再采信"，
不修改不丢弃**——它无法分辨"数据错了"和"市场真的在定价极端情形"，
这个判断必须留给人。

配套：每次 screen 自动把原始基本面快照存档到 `reports/research/data/`
（带抓取时间戳）。排名表是加工品，快照才是证据——人工核验、事后复盘、
跨期对比都需要"当时看到的原始值"。

## 仍然已知的边界（诚实清单）

1. **二手数据的天花板**：免费源都不是交易所直连（台湾官方源除外），
   双源一致只能证明"上游搬运一致"，不能证明与交易所原始数据一致。
   要 institutional 级需要付费源（Polygon/Databento），Provider 协议已预留。
2. **基本面无 point-in-time**：yfinance 快照字段无法回答"当时市场知道
   什么"，限制了基本面策略的回测可信度（行情数据不受此影响）。
   快照存档从现在起逐步积累出自己的 point-in-time 序列，但补不了历史。
3. **预警防线有盲区**：fPE/tPE 同时错、或错得"数学上自洽"的数据
   不会触发预警；预警干净 ≠ 数据正确，只是没抓到已知形态的错。
4. **分钟线只有主源**：所有备源仅日线，日内数据无降级路径。
5. **Naver 备源仍未实网验证**：两轮环境的网络层都没放行（见上文注*），
   解析逻辑只过离线单测——.KS 标的当前事实上没有可用备源：主源被拒时
   只能靠 repair_ohlcv 救急，双源对账不可用。台湾官方/Tiingo 已于
   2026-06-12 实网验收通过（Tiingo 还当场修了一个解析 bug，见上）。
6. **对账非阻断**：对账目前是人工触发的巡检命令，不在每次请求的关键
   路径上（延迟与配额考虑）。
